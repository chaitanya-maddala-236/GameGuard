# Deployment and operations

## Local run

1. Install Python 3.11+ and Docker Desktop with its Linux Engine running.
2. Copy `.env.example` to `.env`; choose a unique `API_KEY` for any shared/public deployment.
3. Run `docker compose up --build` from the repository root. Compose starts PostgreSQL, applies the Alembic migration, then starts the API and dashboard.
4. Check `http://localhost:8000/health`, `http://localhost:8000/ready`, `http://localhost:8000/docs`, and `http://localhost:8501`.
5. Upload source-schema CSV or Parquet through Live Telemetry, or use `python scripts/replay_data.py --rate 10 --limit 100` after downloading the dataset.

For a Python-only local API, install `requirements-dev.txt`, install this project with `python -m pip install -e .`, train the model, then run `python -m gameguard.migrate` and `uvicorn gameguard.api:app --reload`. Run Streamlit in another terminal with `API_BASE_URL=http://127.0.0.1:8000` and `streamlit run dashboard/app.py`. The default database is a local SQLite file; back it up before deleting it.

## Render deployment

The root `render.yaml` creates the API and dashboard using Render Blueprints. Create a separate PostgreSQL project with Neon, select the free plan, and set its pooled connection URL as the Blueprint's `DATABASE_URL` secret when Render prompts for it. Keep the URL out of Git. The API's `API_KEY` is generated by Render and passed to the dashboard over a service reference. `API_BASE_URL` and `ALLOWED_ORIGINS` are resolved from the services' public HTTPS URLs. This is required for the current free Render web-service plan, which does not support private service networking between these services. The Docker image includes the versioned model artifact, not the raw dataset.

The Blueprint selects free Render web services for a public demo. Render documents free web services as sleeping after 15 minutes idle; Neon currently shows this account on its $0/month Free plan, whose per-project allowance includes 1 GB storage and 100 compute hours. Both providers' limits and pricing can change. Confirm the current [Render limits](https://render.com/docs/free) and [Neon plans](https://neon.com/pricing) before relying on the service for sustained production use.

After deploy, open the dashboard URL, then verify API `/health` and `/ready`, inspect the dashboard, and check `/v1/metrics/summary`, `/v1/monitoring`, and `/metrics`. Ingest an explicitly approved, non-sensitive test event only when you need to verify write-path persistence; otherwise keep live traffic metrics empty and report offline evaluation and local synthetic-load results separately. Record provider URLs and the exact checks performed in `docs/deployment-status.md`.

## GitHub Actions

CI runs Ruff formatting/lint, pytest, and a Docker image build for pushes and pull requests to `main`. It does not create releases or deploy. The Render Blueprint provides an explicit manual deployment path after connecting the repository. Never put database passwords or API keys in GitHub files.

## Backups, restart, rollback

- The Render database is the system of record. Set a retention policy and use a paid database with backups for ongoing data. Download periodic `pg_dump` backups and test restore before production.
- API and dashboard containers are stateless; model artifacts are versioned with source. Migrations run during API startup and are checked into `migrations/`.
- Roll back by redeploying a prior Git commit and compatible model artifact. Take a database backup before schema migrations; backward-incompatible schema changes need a coordinated migration.
- Check API logs for validation errors, database failures, and restart loops. `/ready` checks database connectivity and loaded model presence; `/health` checks process liveness only.
